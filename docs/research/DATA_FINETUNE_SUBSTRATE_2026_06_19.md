## Realistic on-device path (mlx-lm LoRA/QLoRA, Apple Silicon)
Overnight on a 16–32GB Mac is REALISTIC for small models: QLoRA of a 7–8B fits ~7GB, a custom adapter run <30–90 min. Trainable lane = MLX safetensors descriptors (Qwen3 4B/8B, Qwen3.5/3.6 0.8–4B, Gemma4 E2B/E4B). **GGUF set (LFM2.5-8B, VibeThinker, Gemma4-QAT) is NOT trainable in-process** (llama.cpp lane) → best overnight targets = Qwen3-4B or Gemma4-E2B/E4B; **LFM2.5 needs an MLX catalog descriptor added** (model classes exist, catalog entry missing). RISK: documented MLX-LM training memory growth/leaks on long runs can OOM the whole app (in-process shares address space) → mitigate with Task.detached, capped iterations, saveEvery checkpointing (exists), memory-pressure abort, bounded dataset. Keep MAS/Pro gating exactly as-is (training Pro/dev only — don't ship in MAS).

## "Another repo" → recommendation: KEEP app-native in-process (don't split)
Epistemos already chose the app-native path (in-process MLX, no sidecar) per the no-hidden-sidecar doctrine. A separate repo/dev tool reintroduces a sidecar + splits provenance. Keep training in-app, Pro-gated, in-process; the vendored `LocalPackages/mlx-swift-lm` IS the embedded engine. Only dataset generation/validation at scale (MOHAWK Python) stays a dev-only out-of-app tool.
