# Goose Surface Parity Fix Plan (2026-06-28)

> 🔴 **SUPERSEDED 2026-07-02 (OpenChamber pivot) — DO NOT BUILD FROM THIS.** Parity-fix plan for the DEAD reskin-Goose-surface program. The agent surface is OpenChamber (Pro) / June+goose-in-process (MAS); goose = one engine. Historical reference only. Canon: memory `project_ui_base_pivot_openchamber_2026_07_02`.

Source: 8-area multi-agent parity audit (Epistemos staged Goose vs real upstream Goose), root-caused. Owner pains: (1) can't change model, (2) no auto-detect of installed providers/CLIs, (3) main providers not ready by default.

## Executive summary

The owner's three named complaints — (1) can't change a provider's model, (2) embedded Goose no longer auto-detects installed providers/CLIs/agents, (3) "main" providers/models aren't ready by default — collapse to a small set of genuinely-fixable graft/ACP bugs, NOT inherent ACP limits. The single highest-leverage bug is in the provider graft: getAcpProviders() (stage-goose-web-ui.sh:500-513) returns the catalog SURFACE on the proven-working happy path, and that surface hardcodes is_configured:false (lines 244, 275) while the only live-configured path (line 224, entry.configured) runs solely inside the catalog-failure catch. The live truth IS already fetched (readAcpProviderConfigStatuses -> providers/config/status, line 565) but is consumed only by the Auth secrets list (line 760) and never overlaid onto the roster. Result: every provider shows "Configure" with no green check, SwitchModelModal.filter(is_configured) yields an empty provider dropdown so no model can be changed, and RecipeModelSelector is starved the same way. Overlaying the already-fetched config statuses (or inverting getAcpProviders to load inventory-first and merge) fixes all three named pains at once, 100% live-from-Goose, with the proven catalog path preserved as fallback. Two more P0s compound the pain: a single shared serialization queue (line 858) wedges the entire surface behind any in-flight prompt/cancel, and the Swift launcher blinds Goose's own detection by (a) handing goose serve a Finder-truncated PATH (GooseRuntimeSupervisor.swift:362-363) so CLI/agent providers and stdio MCP extensions are invisible, and (b) stripping GOOSE_PROVIDER/GOOSE_MODEL from the env allowlist (lines 33-35) so env-configured returning users land on the setup screen. None of the owner's core pain is an architectural limit; the only truly inherent items are multi-window recipe launch, the apps page (no ACP method — goosed serves apps over HTTP only), config keys with no ACP home in goose serve 1.39.0 (GOOSE_MODE/MAX_TURNS/TELEMETRY/SECURITY_*), and the deliberate "API keys off the process env" security posture. 

## Owner-named issues

### Cannot change the model of a provider (Switch models dialog provider dropdown is empty; Model dropdown never loads).
- **Root cause:** getAcpProviders() (stage-goose-web-ui.sh:500-513) returns loadProviderCatalogSurface() on the happy path, whose builders setupCatalogProviderDetails (line 244) and catalogTemplateProviderDetails (line 275) hardcode is_configured:false. SwitchModelModal.tsx:484 does providersResponse.filter(p => p.is_configured) -> empty list, so no provider is selectable and the model-load effect bails at SwitchModelModal.tsx:509-510 (if (!activeProvider) return). The live configured flag (providerDetails line 224, entry.configured) only runs in the catalog-failure catch (line 516), never on the proven path; and the live config/status RPC fetched at line 760 is only used to filter Auth secrets, never overlaid back onto is_configured.
- **Fix:** Overlay live configured status onto getAcpProviders()'s return using the already-wired readAcpProviderConfigStatuses([]) (providers/config/status, empty array returns ALL providers): build byId = Map(statuses.map(s=>[s.providerId,s.isConfigured])) and return list.map(p=>({...p, is_configured: byId.get(p.name) ?? p.is_configured})), wrapped in try/catch that falls back to the un-enriched list. Better still (finding 26), invert getAcpProviders to load providersList_unstable inventory FIRST and mergeProviderDetails(inventory, catalogSurface) (helper already at line 291), so live is_configured + detected models win and the catalog surface only ADDS providers the inventory omits. 100% live-from-Goose, no hardcoded roster, proven catalog path preserved as fallback. Pair with cache invalidation (rank 6) so the green check appears immediately after a key is entered, and with the session-provider guard fix (rank 9) so in-chat switches apply the right provider.

### Embedded Goose no longer auto-detects installed providers/CLIs/agents (every provider shows Configure, no green check; codex/claude/gemini/ollama CLIs invisible).
- **Root cause:** Two independent causes. (a) The is_configured-hardcoded catalog surface above means even API-key providers Goose knows are configured render as unconfigured. (b) The Swift launcher blinds Goose's OWN detection: GooseRuntimeSupervisor.processEnvironment sets env[PATH]=binDir:existingPath (lines 362-363) where existingPath is the launchd/Finder PATH (/usr/bin:/bin:/usr/sbin:/sbin) lacking /opt/homebrew/bin, /usr/local/bin, ~/.local/bin, ~/.cargo/bin, ~/.bun/bin and npm global bin, so Goose's PATH-based CLI/agent detection (codex_acp, claude_code, copilot_acp, gemini, ollama) finds nothing and stdio MCP extensions fail to spawn. The env allowlist (lines 33-35) also omits GOOSE_PROVIDER/GOOSE_MODEL/OLLAMA_HOST so Goose's env-based detection is starved.
- **Fix:** (a) Apply the config-status overlay/inventory-first fix above. (b) In processEnvironment, resolve the user's login-shell PATH once (e.g. $SHELL -lc 'printf %s "$PATH"' under the existing env_clear hygiene) or at minimum union the canonical macOS tool dirs into env[PATH] before prepending binDir, and add GOOSE_PROVIDER, GOOSE_MODEL, GOOSE_DEFAULT_PROVIDER, GOOSE_DEFAULT_MODEL, OLLAMA_HOST and the non-secret GOOSE_* family to the allowlist. Detection stays inside Goose; Swift only supplies search path + host config (like GOOSE_API_HOST), so the GOLDEN RULE holds.

### Main providers/models are not ready by default (lands on Epistemos setup screen; new chat shows Select Model; can fail to create a session).
- **Root cause:** Nothing in the Epistemos boot path establishes goose serve's default provider/model. GooseACPEventBridge.swift:178 calls syncConfiguredProviderKeys (pushes API keys via providers/config/save) but NEVER calls saveGooseDefaults — which exists at GooseACPClient.swift:288 but is unused — and never triggers Goose's onboarding import. So config GOOSE_PROVIDER/GOOSE_MODEL stay unset, defaultsRead returns empty, OnboardingGuard.checkProvider renders setup, and a new chat hits resolve_default_provider_model_config which errors when GOOSE_PROVIDER/GOOSE_MODEL are unset. Compounded by the env-allowlist stripping of GOOSE_PROVIDER (returning users who set it in their shell are not honored) and the model-roster cap of slice(0,8) (stage-goose-web-ui.sh:471) leaving providers past index 8 with default_model:'' / known_models:[].
- **Fix:** In GooseACPEventBridge after syncConfiguredProviderKeys, if readGooseDefaults() returns no providerId: optionally invoke Goose's onboarding import (scan then apply) so Goose auto-detects ~/.config/goose/config.yaml + Claude Desktop, then read the live inventory (providersList_unstable) and, when exactly one provider is configured, call saveGooseDefaults(providerId, entry.default_model). Guard to the single-configured case so it never guesses among several (preserving real-Goose onboarding behavior when ambiguous). Add GOOSE_PROVIDER/GOOSE_MODEL to the env allowlist so env-configured users are honored. Remove the slice(0,8) cap (or lazily call readAcpProviderCatalogTemplate/listAcpProviderModels on selection) so all detected providers carry models. Every value comes live from Goose ACP; no Swift roster.

## Prioritized fixes

### [1] P0 (risk low, golden-rule-safe=True) — Provider auto-detection / model switcher (acp/providers.ts getAcpProviders graft)
- **What:** getAcpProviders() returns the catalog surface with is_configured hardcoded false (stage-goose-web-ui.sh:244,275,500-513); live configured status (line 224 / readAcpProviderConfigStatuses line 565) is never overlaid. Breaks all three owner pains: empty provider dropdown (no model change), no green checks (no auto-detect), providers not ready.
- **Fix:** Overlay readAcpProviderConfigStatuses([]) (providers/config/status) onto the returned list (is_configured = byId.get(name) ?? p.is_configured) in try/catch; OR invert getAcpProviders to load providersList_unstable inventory first and mergeProviderDetails(inventory, catalogSurface) (helper already at line 291). Fallback to un-enriched catalog on RPC failure so the proven path is never broken.

### [2] P0 (risk medium, golden-rule-safe=True) — ACP client serialization (acpConnection.ts serializeACPRequests graft)
- **What:** A single shared `let queue` (stage-goose-web-ui.sh:858) is closed over by both the client and client.goose proxies, so every provider/model/config read serializes behind an in-flight prompt (resolves only at end_turn), and cancel() is queued BEHIND the prompt it should interrupt. withAcpTimeout rejects the wrapper but never frees the chain. Net: whole surface wedges mid-turn and Stop does nothing.
- **Fix:** Exempt long-lived/control methods (prompt, cancel, sessionSteer_unstable, loadSession, newSession) from the queue so they run concurrently; advance `queue` off a settled race (allSettled) so a timed-out/abandoned call frees the chain instead of blocking indefinitely. Pure JS graft, still live-from-Goose.

### [3] P0 (risk low, golden-rule-safe=True) — Swift runtime env allowlist (GooseRuntimeSupervisor.processEnvironment)
- **What:** subprocessEnvironmentAllowlist (lines 33-35) excludes GOOSE_PROVIDER/GOOSE_MODEL/GOOSE_DEFAULT_*/OLLAMA_HOST, so goose serve cannot perform its own env-based detection; returning users who set export GOOSE_PROVIDER/OLLAMA_HOST land on the setup screen.
- **Fix:** Add GOOSE_PROVIDER, GOOSE_MODEL, GOOSE_DEFAULT_PROVIDER, GOOSE_DEFAULT_MODEL, OLLAMA_HOST and the non-secret GOOSE_* family to the allowlist. Detection stays inside Goose; these are host/detection config, not a roster. Keep provider API keys off the process env (security posture); mirror them via the existing Keychain->GooseProviderKeyBridge path instead.

### [4] P1 (risk low, golden-rule-safe=True) — Swift runtime PATH (GooseRuntimeSupervisor.processEnvironment)
- **What:** env[PATH]=binDir:existingPath (lines 362-363) where existingPath is the Finder/launchd-truncated PATH lacking /opt/homebrew/bin, /usr/local/bin, ~/.local/bin, ~/.cargo/bin, ~/.bun/bin, npm global bin. Goose's PATH-based CLI/agent detection (codex/claude/gemini/copilot/ollama) and stdio MCP extension spawning all fail; worked in standalone Goose launched from a shell.
- **Fix:** Resolve the user's login-shell PATH once ($SHELL -lc 'printf %s "$PATH"' under the existing env_clear/hardening) or union the canonical tool dirs into env[PATH] before prepending binDir. Detection still happens entirely inside Goose; Swift only widens the search path.

### [5] P1 (risk low, golden-rule-safe=True) — Boot-time default activation (GooseACPEventBridge / GooseACPClient.saveGooseDefaults)
- **What:** syncConfiguredProviderKeys (GooseACPEventBridge.swift:178) pushes API keys but never activates a default; saveGooseDefaults (GooseACPClient.swift:288) is unused. config GOOSE_PROVIDER/GOOSE_MODEL stay unset -> OnboardingGuard setup screen and new-chat default-resolution error.
- **Fix:** After syncConfiguredProviderKeys, if readGooseDefaults() is empty: optionally trigger Goose onboarding import (scan/apply) to auto-detect existing config, then read live inventory and, when exactly one provider is configured, call saveGooseDefaults(providerId, default_model). Guard to single-configured case. Pure ACP wiring, all values from Goose.

### [6] P1 (risk low, golden-rule-safe=True) — Provider cache invalidation (acp/providers.ts module caches)
- **What:** providerInventoryCache/providerCatalogSurfaceCache (stage-goose-web-ui.sh:369/371) are populated once and never invalidated; getAcpProviders short-circuits on them (501-506). After a user enters a key, the stale all-unconfigured snapshot is frozen until a full reload, so the rank-1 fix won't reflect new config until restart.
- **Fix:** Export resetAcpProviderCaches() that nulls both caches and their in-flight promises; call it at the start of upsertAcpProviderConfig/saveAcpProviderConfig/removeAcpProviderConfig/saveAcpProviderDefaults and from the ConfigContext reloadConfig graft. Pure JS graft, live-from-Goose.

### [7] P1 (risk low, golden-rule-safe=True) — Settings config map (ConfigContext.reloadConfig graft)
- **What:** The ConfigContext graft rewired providers()/readConfig/upsert/remove to ACP but left reloadConfig calling dead REST readAllConfig (ConfigContext.tsx:58-59,170); goose serve serves only /acp,/health,/status so GET /config 404s and setConfig({}) leaves the config map permanently empty. Every Settings section reading the config map (Mode, Max-turns, Telemetry, Security) shows defaults and never reflects saved values.
- **Fix:** Add a USE_ACP_CHAT branch to reloadConfig that reconstructs the config map from live ACP sources (readAcpProviderDefaults for GOOSE_PROVIDER/GOOSE_MODEL + preferences read + provider config statuses) instead of REST readAllConfig.

### [8] P1 (risk low, golden-rule-safe=True) — Settings persistence (acp/providers.ts local-config Map vs preferences)
- **What:** A hardcoded key allowlist (stage-goose-web-ui.sh:587-604) routes Mode/Telemetry/Dictation/Whisper/Security writes into a module-level in-memory Map (localAcpConfigValues) that resets every load and never reaches goose serve; goose exposes a persistent preferences/{read,save,remove} store the graft ignores.
- **Fix:** Route preference-allowlisted keys (GOOSE_THINKING_EFFORT->GooseThinkingEffort, voice_dictation_provider->VoiceDictationProvider, voice_dictation_preferred_mic->VoiceDictationPreferredMic, AutoCompactThreshold) through preferencesSave/Read/Remove_unstable so they persist live from Goose. For keys with no ACP home in 1.39.0 (GOOSE_MODE global, GOOSE_MAX_TURNS, GOOSE_TELEMETRY_ENABLED, SECURITY_*), hide the control in ACP mode rather than presenting a dead toggle.

### [9] P2 (risk low, golden-rule-safe=True) — In-chat model switch (ModelAndProviderContext changeModel graft)
- **What:** Session branch gates the provider write on the GLOBAL default: stage-goose-web-ui.sh:2127 if (providerName && providerName !== currentProvider). currentProvider is the global default (readAcpProviderDefaults), not the session's provider, so picking a model whose provider equals the global default while the session is on a different provider skips saveAcpSessionProvider and applies the model against the wrong provider.
- **Fix:** Drop the `&& providerName !== currentProvider` guard; always await saveAcpSessionProvider(sessionId, providerName) (when truthy) BEFORE saveAcpSessionModel, matching upstream configure.tsx order (setSessionConfigOption provider is idempotent). Can revert the [intl, currentProvider] dep back to [intl].

### [10] P2 (risk low, golden-rule-safe=True) — Provider model rosters (loadProviderCatalogSurface slice cap)
- **What:** loadProviderCatalogSurface fetches per-provider templates only for catalogEntries.slice(0,8) (stage-goose-web-ui.sh:471); every provider past index 8 falls to setupCatalogProviderDetails with default_model:'' and known_models:[], starving the grid and the model picker.
- **Fix:** Remove the slice(0,8) cap (optionally with bounded concurrency), OR lazily call the already-wired readAcpProviderCatalogTemplate(providerId)/listAcpProviderModels(providerId) on selection. Models stay live from goose serve.

### [11] P2 (risk low, golden-rule-safe=True) — Auth settings credential delete (AuthSettingsSection graft + acpProviderSecret)
- **What:** acpProviderSecret hardcodes can_delete:false (stage-goose-web-ui.sh:743) so the Delete control never renders, and confirmDelete still calls dead REST deleteProviderSecret with a synthetic id REST cannot resolve. A wrong/expired key can't be removed in ACP mode, though goose supports providers/config/delete (deleteAcpProviderConfig line 710).
- **Fix:** Set can_delete:true and add an AuthSettingsSection graft branch so confirmDelete calls deleteAcpProviderConfig(secret.provider) under USE_ACP_CHAT, then reload via listAcpProviderSecrets().

### [12] P2 (risk medium, golden-rule-safe=True) — Provider key save rollback (DefaultSubmitHandler graft)
- **What:** On key save the graft calls validateAcpProviderModels(provider.name) which throws when zero supported-models come back (live provider.fetch_supported_models can error/return empty for some providers/networks), and on throw rolls back the just-saved valid credential, leaving the provider unconfigured.
- **Fix:** Treat empty/failed supported-models as a non-fatal warning; do NOT roll back. Fall back to the live catalog known_models (provider.metadata.known_models), matching the modelInterface.ts getModelsForProvider pattern (stage-goose-web-ui.sh:1735-1781). Keep the saved key; surface a soft warning.

### [13] P2 (risk low, golden-rule-safe=True) — Skills/Sources project scope (GooseWebBootShim workingDirectory)
- **What:** GOOSE_WORKING_DIR is pinned to home (GooseWebBootShim.swift:15); SkillsView passes it as projectDir to sources/list, so project-local skills under <project>/.goose/skills are filtered out server-side. Regression vs standalone Goose which scopes discovery to the opened directory.
- **Fix:** Feed the user's active vault/project dir into GooseWebConfig.workingDirectory when constructing GooseWebBootstrap (GooseWebSurfaceView.swift:28) and update it on project switch via the existing GOOSE_WORKING_DIR path. Optionally pass include_project_sources:true. Detection stays live from sources/list; only the scanned projectDir changes (host config, not a roster).

### [14] P2 (risk medium, golden-rule-safe=True) — Apps page source-of-truth (epistemos/appsBridge.ts + GooseWebBootShim epistemosGooseApps)
- **What:** The apps bridge delegates to a Swift localStorage store (GooseWebBootShim.swift:256-272, loadImportedApps/saveImportedApps) that never queries Goose and discards session_id. Chat-generated and standalone-imported apps never appear — a GOLDEN-RULE violation (app-maintained roster replacing the live Goose source).
- **Fix:** Point the bridge at goosed's own HTTP routes GET /agent/list_apps?session_id=<id>, POST /agent/import_app, GET /agent/export_app/{name} against GOOSE_API_HOST with the X-Secret-Key header (same goosed instance ACP talks to). Note: apps have NO ACP method, so HTTP is the only live transport. localStorage may remain an offline cache only, never source of truth.

### [15] P2 (risk low, golden-rule-safe=True) — Staging graft integrity (stage-goose-web-ui.sh conditional replaces + validate gate)
- **What:** Several provider grafts use if(source.includes(anchor)){replace} with NO else-throw and are not covered by the VALIDATE_ONLY grep gate (DefaultSubmitHandler readConfig/modelValidation, ProviderConfigurationModal OAuth/cleanup). On upstream drift they silently no-op while USE_ACP_CHAT stays true, leaving dead REST/Electron calls live that fail only at runtime. The SkillsView reskin also exists only as an uncommitted working-tree edit, not a codified graft.
- **Fix:** Convert these conditional replaces to replaceRequired-style hard edits (throw if anchor absent or result unchanged) and add their marker snippets to the EPISTEMOS_GOOSE_UI_VALIDATE_ONLY grep gate. Codify the SkillsView getDisplaySkill reskin as an anchor-based graft (same pattern as the recipe_management block at 2538-2631). Pure staging-script change.

### [16] P3 (risk low, golden-rule-safe=True) — Switcher pre-selection (acp/providers.ts saved_model)
- **What:** SwitchModelModal.tsx:604-608 auto-selects providerInfo.saved_model, but the grafted ProviderDetails builders never populate saved_model, so the dialog falls back to a heuristic findPreferredModel instead of the provider's actually-saved model.
- **Fix:** Populate saved_model on the grafted ProviderDetails from live Goose state (entry.defaultModel in providerDetails, and readAcpProviderDefaults for the active provider). Sourced from ACP, never hardcoded. Low priority; picker is usable without it.

### [17] P3 (risk low, golden-rule-safe=True) — External links (GooseWebBootShim / WKWebView UI delegate)
- **What:** window.open(url,'_blank') no-ops (Extensions 'Browse extensions', docs links): the boot shim exposes only window.electron.openExternal and the WKWebView host sets no WKUIDelegate, so WKWebView ignores window.open with no handler.
- **Fix:** Add a WKUIDelegate whose createWebViewWith routes external http(s) URLs to NSWorkspace.shared.open and returns nil, OR a one-line boot-shim polyfill overriding window.open to call postNativeAffordance('openExternal',[url]). UI-only; touches no ACP/detection.

## Architectural limits (do NOT graft away)

Separating fixable graft/ACP bugs from inherent ACP-vs-Electron limits: ALL THREE of the owner's named pains (can't change model, no auto-detect, not-ready-by-default) are fixable graft/ACP/launcher bugs — none is an architectural limit. The is_configured overlay, serialization queue, cache invalidation, PATH/env, boot-defaults, reloadConfig and preferences fixes are all pure stage-goose-web-ui.sh grafts or ACP/host-config wiring with the live-from-Goose GOLDEN RULE intact.

Genuinely inherent ACP-vs-Electron limits (do NOT try to graft away): (1) Multi-window — recipe 'Open in new window' / window.electron.createChatWindow assume Electron BrowserWindows; Epistemos is a single WKWebView host, so this is single-window by design (the recipe still runs in-window). A true second window needs a new GooseSurfaceWindowController, not a graft. (2) Apps page — goose serve exposes NO ACP method for apps; goosed serves them only over HTTP REST (/agent/list_apps, /agent/import_app, /agent/export_app). Restoring live apps requires the bridge to hit goosed HTTP directly; the current localStorage roster is a GOLDEN-RULE violation, but the fix is a different transport (HTTP), not ACP. (3) Config keys with no ACP home in goose serve 1.39.0 — GOOSE_MODE (global default), GOOSE_MAX_TURNS, GOOSE_TELEMETRY_ENABLED, SECURITY_* have no preferences/config ACP surface; these controls should be HIDDEN in ACP mode rather than backed by a dead in-memory Map. (4) Provider API keys off the process env — GooseRuntimeSupervisor's denylist stripping OPENAI_API_KEY/ANTHROPIC_API_KEY/etc. (lines 68-96) is an INTENTIONAL security posture, not a regression; standalone-Goose-from-terminal parity (env keys auto-detected) conflicts with it. The GOLDEN-RULE-safe reconciliation is to capture any present provider-key env vars into Epistemos Keychain at launch so the existing GooseProviderKeyBridge mirrors them into Goose's own provider-config over ACP — NOT to re-add keys to the subprocess env. This is the one medium-risk area where 'parity with standalone' and 'keys off process env' genuinely trade off; everything else is a clean fix.

Dependency ordering: rank 1 (is_configured overlay) needs rank 6 (cache invalidation) to be visible after the user enters a key, and rank 9 (session-provider guard) to make in-chat switches land on the right provider; rank 5 (boot defaults) and rank 3/4 (env+PATH) together restore 'ready by default' and CLI/agent auto-detect. Findings 15 (recipe selector) and most of the 'no auto-detect' duplicates require NO code in their own files — they inherit correctness from rank 1 once the provider inventory reports configured=true.
